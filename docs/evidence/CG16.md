# CG16 NiFi -> HTTP -> Elasticsearch real

Flujo vivo: ConsumeKafka, ExtractText, ConvertRecord(CSVReader/JsonRecordSetWriter),
validación Groovy, InvokeHTTP a scoring-api:8000/predict, EvaluateJsonPath y
PutElasticsearchJson. Respuesta conserva identidad/fecha/sensores/versiones.
La rama alerta usa RouteOnAttribute (alert_level distinto OK o anomaly_alert=true)
y otro índice. Todos los documentos llevan _id=event_id para reintentos idempotentes.

Se han indexado 31 documentos y una alerta en v1, de32 mensajes (uno numérico
inválido conservado en state/rejected). Los primeros20 incluyen el reenvío inicial
antes de corregir Filebeat; no se presentan como20 observaciones nuevas.
HTTP fallo/retry va a RetryFlowFile máximo2;422 y rechazos van a envoltura con
raw_record, clave, razón/status y contador. No hay worker alternativo a NiFi ni
segunda preparación RF. Las decisiones se calculan solo en la API.

Durante montaje del routing se archivaron también20 normales en state/quarantine;
se conservan y se distinguen de los rechazos de la configuración final, en
state/rejected. El routing normal final no los envía allí. No se eliminan registros
para mostrar un resultado ideal. Export actual: cnc_lab_completed.json, con
propiedades de los procesadores2.0 instalados, sin placeholder SplitRecord.

Se detectó además que un fingerprint después de la fecha puede hacer colisionar
lecturas con iguales sensores en horas distintas. Se probará una versión de
laboratorio v2 separada para corregirlo sin borrar topic, registry o índicesv1.
El ensayo usa snapshots/sintéticos; no establece rendimiento estadístico o SMB vivo.
