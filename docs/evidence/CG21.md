Esta PR conserva su historia y conecta el harness al `consume` existente de

## Reproducir en Linux

Desde la raíz, con el entorno fijado en `uv.lock`:

```bash
uv run --frozen python -m unittest tests.test_failure_harness tests.test_archive_consumer tests.test_contract_validation -v
uv run --frozen python -m unittest discover -s tests -p test_api_client.py -v
uv run --frozen python -m scripts.failure_harness --output outputs/cg21-nueva-ejecucion
```

La ruta debe estar ausente o vacía. Se rechaza un directorio con cualquier archivo
para conservar evidencia ajena. El resultado contiene `journal.sqlite`,
`journal.archive/` y `report.json`; los subdirectorios `after_write`,
`before_commit` y `after_commit` conservan sus propios journals y archivos.
No reutilizar journals del fixture SQLite antiguo: su tabla `stored` no era CG15.
`CG21_fixture.json` conserva ese antecedente; la nueva ejecución está en
[CG21_durable_20261021.json](CG21_durable_20261021.json).

## Contrato y conciliación

El journal local conserva payload y estado por entrega. Cada offset tiene identidad
estable `cg21/telemetry/<offset>` dentro de su archivo aislado. El sink CG15 recibe
bytes originales, valida el contrato JSON Schema y conserva Bronze, Parquet y
rechazados. El acuse actualiza el journal solamente en el callback posterior al
commit durable de CG15. La identidad no se comparte entre ejecuciones ni pretende
representar un offset Kafka real.

`sent = accepted + rejected + pending` cuenta entregas. `stored_unique` se consulta
en `events` del ledger CG15, y `duplicates` cuenta entregas cuyo outcome es
`duplicate`. Un replay de la misma entrega no aumenta esos contadores.
`offset_acknowledged` es el prefijo local sin pendientes, incluyendo los rechazos
que ya quedaron archivados. Los rechazos conservan payload original en Bronze y
el detalle del error en `rejected/`; el journal guarda `archive_rejected`.

La secuencia original sigue ofreciendo dos eventos válidos, una repetición,
un campo obligatorio ausente y JSON malformado. La indisponibilidad simulada
mantiene cinco pendientes. La escritura sin acuse deja un evento durable y los
cinco pendientes. Tras reapertura y drenaje por lotes:
`5 = 3 accepted + 2 rejected + 0 pending`, `stored_unique=2`, `duplicates=1`,
prefijo local=5. Otro drenaje no altera el resultado.

Además, tres procesos locales independientes terminan con `os._exit(73)` en los
checkpoints reales de CG15: `after_write`, `before_commit` y `after_commit`.
No ejecutan cierre limpio del consumidor ni de SQLite. Antes del replay la fuente
sigue pendiente en los tres casos; sólo `after_commit` tiene una entrega confirmada
en el ledger. La recuperación concilia archivos huérfanos o la entrega ya
confirmada, conserva los bytes Parquet anteriores y acusa una única entrega.
El informe registra el código de salida, los contadores y los hashes antes de
replay. No simula pérdida de alimentación ni prueba garantías del hardware.

Los tests adicionales verifican cuarentena de un event_id con contenido distinto,
conservación de todos los bytes Bronze, bloqueo del acuse ante corrupción de un
archivo confirmado, rechazo de una identidad de entrega reutilizada con otros
bytes, límites de lote y protección del directorio de salida. Los tests de API
usan la aplicación y el lifespan reales mediante `tests.api_client`, sin sockets
ni modelos entrenados nuevos. Manifiesto/artefacto ausente o alterado mantiene 503
y no deserializa el modelo inválido.

## Validación y límites

La ejecución local usa FedoraLinux-43, Python 3.11.15, FastAPI 0.133.0,
Starlette 1.7.0 y PyArrow 23.0.1. Los comandos y resultados completos quedan en
el registro local `recovery-capacity-evidence/` del taskroot. Ruff 0.17.1 se
ejecuta con reglas del proyecto, selección `E,F,I,PLW1510` y format check;
también se ejecutan contratos, auditoría de fuentes, layout y batería estricta.
El registro de entrega distingue sus resultados de CI y revisión independiente.

Resultado ejecutado: 20 tests focalizados y 3 del helper API, sin fallos;
batería estricta completa de 192 tests en cada una de dos pasadas, tres omitidos
por Elasticsearch desechable sin configurar en cada pasada, cero fallos, errores, warnings y
excepciones no capturadas. Contratos, auditoría de fuentes y layout correctos.
Los tres cortes de proceso del fixture alcanzaron su checkpoint y preservaron
los bytes Parquet al recuperar. La verificación separada de los artefactos
comprueba integridad SQLite, todos los hashes confirmados y los payloads Bronze.
La batería completa reutiliza el bundle sintético local preexistente del clon;
no se ejecuta entrenamiento ni empaquetado de un modelo de entrega.

G46/G80/G90/G95/G96 → harness y tests → comandos anteriores → conciliación del
sink CG15 en disco local → límite de proceso único y fuente SQLite → revisor y
fecha pendientes. Esta trazabilidad contribuye evidencia; no certifica todos los
descriptores de la rúbrica.

No hay acceso a NiFi/Kafka/Elasticsearch, SMB/OT ni infraestructura compartida.
La indisponibilidad y el límite de lote son controles del fixture, no fallos de
red o backpressure de broker. La recuperación distribuida, los offsets reales,
el scoring con bundle válido y los conteos ES requieren su laboratorio y revisión
correspondientes. No se ha entrenado un modelo de entrega ni utilizado el test final.
