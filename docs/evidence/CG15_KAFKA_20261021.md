## Laboratorio de protocolo en loopback

Comando real ejecutado:

```bash
uv run --locked --extra kafka --with confluent-kafka==2.16.0 python tests/kafka_wire_lab.py
```

**Exit 0**, librdkafka mock 2.16.0. El script crea su propio endpoint
`127.0.0.1:<puerto efímero>` y un topic, publica tres fixtures con KafkaProducer
real y ejecuta la CLI en subprocesos. Resultado: `sent=3`, `stored=1`,
`duplicate=1`, `rejected=1`; offset del grupo consultado por el cliente = **3**.
Otro grupo, mismo namespace/raíz: **replay=3**, sin cambiar los hashes Parquet
ni añadir entregas. SIGTERM real, tras instalarse el handler y sin nuevos datos:
**salida 0**, sin procesar ni confirmar un lote nuevo.

El mock soporta ApiVersions hasta v2; la negociación automática inicial v4 del
cliente falló en el primer intento con `Unable to decode response` y timeout.
La configuración final selecciona explícitamente API **3.7** por defecto,
coherente con el Compose del proyecto; el lab selecciona **2.0**. No se parcheó
el cliente ni se presentó el intento fallido como aprobado. Un segundo intento
del harness envió SIGTERM demasiado pronto; el harness final espera observar
el handler instalado en `/proc` antes de enviar la señal.

Límite: el mock utiliza sockets y protocolo Kafka, **no es un broker Apache
Kafka 3.7**. Los rebalance/fallos de persistencia/commit se inyectan en las
pruebas focales; no se ha demostrado tolerancia de un clúster Kafka desplegado.
