# CG29 Filebeat -> Kafka

Filebeat9.5.4 filestream, volumen registry persistente y fuente montada read-only.
Salida Kafka con codec message raw; clave path+byte-offset conserva referencia de
origen para normalización. ACK all con un broker no es redundancia.
Header CSV excluido. Fingerprint offset200/length64 cae después del header164B;
muestrear los primeros64B habría hecho colisionar lotes con la misma cabecera.
Archivos menores de264B requieren comprobar el modo growing de esta versión;
no se supone comportamiento de otras versiones. No cambiar fingerprint en una
instalación con registry sin planificar reingesta.

Prueba local: 10 filas -> 10 mensajes, sin cabecera. Tras restart con registry y
rename del archivo, contrastar offset; CG29_filebeat.json conserva resultado.
No es garantía exactly-once: conciliación de event_id en destino evita inflar
conteos ante retries. La interrupción SMB real y permisos del mount siguen sin
probar: se usó snapshot local, sin credenciales ni servidor remoto.

`docker compose run --rm --no-deps filebeat --strict.perms=false test config`:
Config OK. El flag solo evita exigir que el bind de configuración del usuario
pertenezca a root; se monta read-only. No cambia permisos del host.

Fuentes oficiales contrastadas:
https://www.elastic.co/docs/reference/beats/filebeat/file-identity
https://www.elastic.co/docs/reference/beats/filebeat/filebeat-input-filestream

Ensayo adverso: la combinación restart+rename inicial reenvió el lote (offset10→20).
El registry mostraba una entrada con ttl0 y cursor borrado. Se desactiva clean_removed
y cierre por desaparición para no perder estado ante renames/share temporalmente
inaccesible. La clave se refuerza a SHA256 de message + byteoffset, independiente
del nombre: reintentos de esa línea mantienen identidad. No es hash completo del
archivo y no prueba independencia estadística entre emisiones. El estado anterior
se conserva como evidencia; no se borra el topic ni registry para ocultar el fallo.
